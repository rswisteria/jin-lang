# Jin v1 言語マニュアル

Jin（陣）は、AIエージェントの構成と処理の流れを記述する言語です。ひとつの `.jin` ファイルから、構成を表す魔法陣と、Google ADKで実行するPythonコードを生成できます。

このマニュアルは、変数・関数・条件分岐・ループを理解している人を対象にしています。AIエージェントやADKの知識は前提にしません。初めて読むときは第1〜8章を順に進め、記述中に困ったときはフィールド表や診断一覧を参照してください。

対象は `version: 1` と、このリポジトリの実装です。ADKへの変換は、現在の生成コードが対象とする **google-adk 2.8.0** に基づきます。将来の機能や、ADK単体で使える機能がすべてJinでも使える、という意味ではありません。

## 1. Jinで記述するもの

AIエージェントは、モデルへの指示、使える道具、実行中の記憶を組み合わせた処理単位です。Jinでは、この単位を **陣（circle）** と呼びます。

陣には2種類あります。モデルを持つ陣は、自然言語の指示を受けて応答を作り、必要に応じて道具を選びます。モデルを持たない陣は、別の陣を順番に動かすなど、処理の進行を担当します。

| 通常のプログラミングでの考え方 | Jinで近い役割を持つもの | 違い |
|---|---|---|
| 関数やモジュール | `circle` | 引数と戻り値だけでなく、指示・道具・記憶を持つ |
| 関数の処理内容 | `instruction.rune` | 自然言語の指示。計算手順や出力の正しさを厳密には保証しない |
| 処理間で共有する変数 | `state` | 型名は宣言できるが、v1では値の型検査をしない |
| 外部関数の呼び出し | `tools` | 実際に呼ぶかどうかや引数は、通常はモデルが決める |
| 順次処理・並列処理・反復 | `flow` | 実行する陣と順序を明示する |

Jinはエージェントを組み合わせるための宣言的な言語です。`.jin` 内にPythonの文や任意の計算式は書きません。細かな計算や外部サービスへの接続は、Python関数として用意して参照します。

同じファイルから同じ魔法陣が描かれても、実モデルの応答が毎回同じになるとは限りません。**図の再現性と、AIによる処理結果の再現性は別です。**

## 2. 最小のプログラムを動かす

[READMEのセットアップ](../README.md#エディタの実行方法)を済ませてください。以降のコマンドは、リポジトリのルートで実行します。

次の内容を `hello.jin` に保存します。これは省略のない、ひとつのプログラムです。

<!-- example: hello -->
```json
{
  "$schema": "https://xtone.internal/jin/schemas/jin.schema.json",
  "version": 1,
  "root": "Greeter",
  "circles": [
    {
      "name": "Greeter",
      "core": "gemini-2.5-flash",
      "instruction": {
        "rune": "利用者に日本語で短く挨拶してください。"
      }
    }
  ]
}
```

`root` は最初に動く陣の名前です。`circles` にその陣を定義し、`core` で使うモデル、`instruction.rune` で指示を指定します。

```bash
uv run jin check hello.jin
uv run jin editor hello.jin
```

エディタを終了したら、疑似モデルで実行できます。

```bash
uv run jin run hello.jin "こんにちは" --model fake
```

`--model fake` はAIモデルを呼び出さず、固定の `fake-response` を返します。ここでは指示文どおりの挨拶にはなりません。モデルの認証設定を済ませてこのオプションを外すと、`core` に指定した実モデルを使います。

## 3. ファイル形式と基本規則

### 3.1 JSONで保存する

ファイルの拡張子は `.jin`、文字コードはUTF-8、中身はJSONです。文字列は二重引用符で囲み、真偽値は `true` / `false` と書きます。コメント、末尾の余分なカンマ、同じオブジェクト内の重複キーは使えません。

v1は単一ファイルで完結します。他の `.jin` を読み込む `import` はありません。後で説明する `ref` はPythonコードへの参照であり、Jinファイルを取り込む機能ではありません。

### 3.2 ファイル全体のフィールド

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `$schema` | 文字列 | 必須 | 使用するスキーマを示す。標準の値は上の例を参照 |
| `version` | 整数 `1` | 必須 | Jinの形式バージョン |
| `root` | 文字列 | 必須 | 実行・既定の描画の入口となる陣名 |
| `circles` | 陣の配列 | 必須 | ファイル内の陣の定義 |

`$schema` は、実行時に外部からプログラムを読み込むURLではありません。`jin check` は内部のモデル定義で検証し、このURLへスキーマを取得しに行きません。公開スキーマの実体は [jin.schema.json](../schemas/jin.schema.json) です。

陣は名前で参照するため、使う陣より後に定義してもかまいません。`circles` の並びは保存時に保持されますが、実行順は `root` と参照関係、`flow.steps` で決まります。ファイルにあるすべての陣を上から実行するわけではありません。

### 3.3 型、省略、文字列の上限

未知のフィールドはエラーです。`"max": "3"` を整数の `3` とみなすような暗黙の型変換もしません。

省略可能なフィールドには既定値があります。たとえば `tools` を省略すると空配列、`state` の `out` を省略すると `false` です。`core`、`description`、`instruction`、`flow`、`boundary`、`flow.max`、`flow.exit` は `null` でも未指定を表せます。配列フィールドに `null` を書くことはできません。

| 文字列の用途 | 最大文字数 | 例 |
|---|---|---|
| 名前・参照・型名・モデル名 | 128 | `name`、`root`、`ref`、`core`、`type` |
| 自由記述 | 65,536 | `description`、`rune`、文字列の `equals` |
| スキーマの識別文字列 | 2,048 | `$schema` |

名前などの文字列には制御文字を使えません。自由記述では改行・復帰・タブのみ使用できます。UTF-8として表せない孤立サロゲートも拒否されます。JSONの入れ子には64段の上限があります。これは陣どうしの呼び出し深さの制限とは別です。

## 4. 陣を定義する

### 4.1 陣のフィールド

| フィールド | 型 | 省略時 | 役割 |
|---|---|---|---|
| `name` | 文字列 | 省略不可 | ファイル内で一意の陣名 |
| `core` | 文字列または `null` | なし | AIモデルの指定 |
| `description` | 文字列または `null` | なし | この陣が担当する役割の説明 |
| `instruction` | オブジェクトまたは `null` | なし | `rune` に自然言語の指示を書く |
| `tools` | 道具の配列 | `[]` | モデルが使える道具 |
| `delegate` | 陣名の配列 | `[]` | 仕事を引き継げる陣 |
| `state` | 記憶の配列 | `[]` | 記憶の名前と出力先の宣言 |
| `flow` | オブジェクトまたは `null` | なし | 別の陣を動かす順序・反復 |
| `boundary` | オブジェクトまたは `null` | なし | 処理前後のチェックと応答待ち |

`core` と `flow` は、値を持つものを**どちらか一方だけ**指定します。両方ある場合も、両方ない場合も `JIN022` です。

### 4.2 モデルを持つ陣

`core` のある陣は、生成時にADKの `LlmAgent` になります。`core` はモデル名として渡され、`instruction.rune` はモデルへの指示になります。`description` は役割の説明であり、`rune` の代わりではありません。

`tools` と `state` は、それぞれ1つの陣につき最大12個です。多くなる場合は、担当を分けて別の陣に切り出します。`state` のうち `out: true` にできるのは、実行可能な構成では最大1個です。

### 4.3 進行を担当する陣

`flow` のある陣は、指定に応じて順次・並列・反復の進行役になります。自然言語で次の処理を選ぶのではなく、`flow` の記述に従います。

実行する構成では、`instruction`、空でない `tools` / `delegate`、`out: true` の記憶は使えません。担当となるモデル付きの陣に移してください。`description`、出力先ではない `state` の宣言、陣全体の前後に行うチェックは指定できます。

これらの組み合わせには、`jin check` では通ってもコード生成時に拒否されるものがあります。検証の段階は[第10章](#10-検証してエラーを直す)で説明します。

## 5. 指示と記憶をつなぐ

### 5.1 指示文に値を埋め込む

`instruction` に書けるフィールドは、必須の文字列 `rune` です。次は陣の中に書く部分例です。

```json
{
  "instruction": {
    "rune": "次の下書きをレビューしてください。\n{draft}"
  }
}
```

`{draft}` は記憶 `draft` の値を埋め込む指定です。式の評価ではないため、`{draft.length}` や `{count + 1}` による計算はできません。

Jinが参照として読む名前は `[A-Za-z_][A-Za-z0-9_]*` の形です。先頭は英字か `_`、続きには数字も使えます。参照する名前は、後述の可視範囲で宣言されている必要があります。

Jinの静的な読み取りでは `{{` と `}}` をエスケープとして扱いますが、現在のADK変換とは解釈が異なります。`{{draft}}`、`{draft}}`、`{key?}`、`{artifact.x}`、`{app:key}` などは生成時に拒否されます。実行する指示文の埋め込みには、素の `{key}` を使ってください。

### 5.2 記憶を宣言し、応答を保存する

記憶の1要素は次の形です。

```json
{
  "name": "draft",
  "type": "str",
  "out": true
}
```

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `name` | 文字列 | 必須 | 記憶を参照する名前。同じ陣の中で一意 |
| `type` | 文字列 | 必須 | 読み手とエディタのための型名 |
| `out` | 真偽値 | 任意 | `true` なら、この陣の応答を保存する。既定は `false` |

`out: true` はADKの `output_key` に対応します。モデルの応答テキストがその名前で保存されます。`out: false` は「入力値を自動で受け取る」という意味ではありません。利用者の入力を `query` という記憶へ自動代入する規則もありません。

`type` はv1では型検査に使いません。`"type": "bool"` と宣言しても、応答が自動で真偽値になることはありません。値の初期値を宣言する `value` や `default` といったフィールドもありません。

### 5.3 どの記憶を参照できるか

Jinは指示文の参照を、実行前に検査します。ここでいう「可視」は、静的検査でその名前を使ってよい、という意味です。値がすでに計算済みであることまで保証するものではありません。

| 参照したい記憶の宣言場所 | 指示文から参照できるか |
|---|---|
| 自分の陣 | できる。`out` の有無は問わない |
| `sequence` の前の兄弟、その配下の陣 | できる |
| `sequence` の後の兄弟 | その関係だけではできない |
| `loop` のほかの兄弟、その配下の陣 | できる。次の周回では先に実行済みになりうるため |
| `parallel` のほかの兄弟 | その関係だけではできない。順序が保証されないため |
| `delegate` で自分に引き継ぐ親 | できる。親から子の向きに限る |
| `summon` で自分を呼ぶ陣 | その呼び出し関係からの可視性は保証しない |

「配下」は `flow.steps` と `delegate` をたどって到達する陣です。`summon` の呼び出し先は含みません。入れ子の進行役があるときは、祖先ごとにこの規則を適用します。進行役の `state` に宣言しただけで、すべての子へ自動的に見えるようになるわけではありません。

`flow.exit.key` は、その進行役から見える記憶に加えて、`steps` の各陣とその配下の記憶を参照できます。ループ内で作った値を、ループの終了条件に使えるためです。

### 5.4 初期化と共有

`jin run` は、全陣で宣言した記憶を実行開始時に `None` で初期化します。指示文への埋め込み時は空文字として扱われます。たとえばループの1周目に、まだ動いていない担当の出力を参照しても、前回の出力が存在するわけではありません。

記憶は、通常の関数のローカル変数のように陣名で自動的に分離されません。同じセッションで同じ名前に保存すると、同じキーの更新になります。これは下書きを上書きする用途には便利ですが、意図せず情報を失う原因にもなります。

並列の担当には `research_a` と `research_b` のように異なる保存先を与え、終了後の担当でまとめてください。v1には、同じキーへの並列書き込みの競合を検出したり、値を自動で合成したりする規則はありません。

## 6. 処理の順序と繰り返しを指定する

### 6.1 `flow` のフィールド

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `kind` | `"sequence"` / `"parallel"` / `"loop"` | 必須 | 進め方 |
| `steps` | 陣名の配列 | 必須 | 実行する担当。オブジェクトを直接埋め込まず名前で参照する |
| `max` | 1以上の整数、または `null` | 任意 | `loop` の最大周回数 |
| `exit` | 終了条件、または `null` | 任意 | `loop` の終了判定 |

値を持つ `max` と `exit` は `loop` 専用です。`loop` では、その少なくとも一方が必要です。

### 6.2 順次処理と並列処理

`sequence` は `steps` の配列順に実行します。`parallel` は各担当を並行して進めるため、開始・終了・イベント到着の順序を配列順とみなしてはいけません。

次の完全な例を `compare.jin` に保存すると、「2つの観点で並列に検討し、両方が終わったらまとめる」構成になります。

<!-- example: compare -->
```json
{
  "$schema": "https://xtone.internal/jin/schemas/jin.schema.json",
  "version": 1,
  "root": "Compare",
  "circles": [
    {
      "name": "Compare",
      "flow": { "kind": "sequence", "steps": ["Perspectives", "Reporter"] }
    },
    {
      "name": "Perspectives",
      "flow": { "kind": "parallel", "steps": ["Benefits", "Risks"] }
    },
    {
      "name": "Benefits",
      "core": "gemini-2.5-flash",
      "instruction": { "rune": "利用者の提案の利点を挙げてください。" },
      "state": [{ "name": "benefits", "type": "str", "out": true }]
    },
    {
      "name": "Risks",
      "core": "gemini-2.5-flash",
      "instruction": { "rune": "利用者の提案のリスクを挙げてください。" },
      "state": [{ "name": "risks", "type": "str", "out": true }]
    },
    {
      "name": "Reporter",
      "core": "gemini-2.5-flash",
      "instruction": { "rune": "利点: {benefits}\nリスク: {risks}\n両方を踏まえて提案をまとめてください。" },
      "state": [{ "name": "report", "type": "str", "out": true }]
    }
  ]
}
```

`Reporter` から見ると、`Perspectives` は同じ `sequence` の前の枝です。その配下の `benefits` と `risks` の両方を参照できます。一方、`Benefits` と `Risks` は並列の兄弟なので、互いの出力を前提にしません。

```bash
uv run jin check compare.jin
uv run jin run compare.jin "大学図書館を24時間開館にする" --model fake
```

### 6.3 反復と終了判定

`loop` は、1周につき `steps` を先頭から順番に動かします。`exit` がある場合、Jinは最後に判定役を追加します。条件を先に調べる `while` 文と違い、通常の進行では**本体を実行した後**に条件を調べます。

次を `approval.jin` に保存します。

<!-- example: approval -->
```json
{
  "$schema": "https://xtone.internal/jin/schemas/jin.schema.json",
  "version": 1,
  "root": "Approval",
  "circles": [
    {
      "name": "Approval",
      "flow": {
        "kind": "loop",
        "steps": ["Judge"],
        "max": 3,
        "exit": { "key": "approved", "equals": true }
      }
    },
    {
      "name": "Judge",
      "core": "gemini-2.5-flash",
      "instruction": {
        "rune": "利用者の提案が実行可能か判断してください。応答はJSONの真偽値 true または false だけにしてください。"
      },
      "state": [{ "name": "approved", "type": "bool", "out": true }]
    }
  ]
}
```

`Judge` の応答を `approved` に保存してから終了条件を確認します。一致すれば終了し、一致しなければ次の周回へ進みます。条件が成立しなくても、3周で終了します。`max` はモデルの総呼び出し回数や秒数ではなく、ループの周回数です。

この例は同じ担当を反復する仕組みの例です。前回の結果を使って自動的に提案を改善する処理はありません。また、自然言語で出力形式を指定しても、その形式が必ず守られる保証はありません。

`exit` だけを指定して `max` を省略することもできますが、条件が成立しなければ終了しない可能性があります。最初は両方を指定すると、試行の回数を把握しやすくなります。モデルが組み込み道具 `exit_loop` を呼ぶなど、ループ途中で終了を要求する経路もあります。

### 6.4 終了条件の比較規則

`exit` の `key` は記憶名、`equals` は比較する値です。両方必須です。`equals` に使えるのは文字列・真偽値・整数・数値で、`null`、配列、オブジェクト、比較式は指定できません。大小比較や複数条件のAND / ORもありません。

| `equals` | 記憶の実際の値 | 一致するか | 理由 |
|---|---|---|---|
| `true` | 文字列 `"true"` | 一致 | JSONの真偽値として読める |
| `true` | 文字列 `"True"` | 不一致 | JSONの真偽値は小文字 |
| `true` | 文字列 `"1"` | 不一致 | 数値と真偽値は別の型 |
| `true` | 文字列 `"approved=true"` | 不一致 | JSONの単一の値として読めない |
| `3` | 文字列 `"3.0"` | 一致 | 数値として等しい |
| `"yes"` | 文字列 `" yes "` | 一致 | 文字列同士は両辺の前後の空白を除く |
| `"true"` | 真偽値 `true` | 不一致 | 期待値が文字列のときは文字列同士で比較する |

期待値が真偽値か数値で、記憶が文字列なら、前後の空白を除いてJSONとして読みます。読み取れない場合は不一致です。記憶がすでに真偽値や数値なら、型を区別して値を比較します。Pythonの `True == 1` のような一致は採用しません。

## 7. 道具と別のエージェントを使う

### 7.1 道具の3つの種類

`tools` の各要素には `name` と `kind` が必要です。`kind` に応じて、もう1つの必須フィールドが変わります。次は `tools` 配列の部分例です。`Summarizer` は別途定義する陣です。

```json
[
  { "name": "search", "kind": "tool", "ref": "research.tools:web_search" },
  { "name": "finish", "kind": "builtin", "builtin": "exit_loop" },
  { "name": "summarize", "kind": "summon", "circle": "Summarizer" }
]
```

| `kind` | 必須の追加フィールド | 実行時の役割 |
|---|---|---|
| `tool` | `ref` | Python関数を `FunctionTool` として使う |
| `builtin` | `builtin` | ADKの公開する組み込みツールを使う |
| `summon` | `circle` | 別の陣を `AgentTool` として呼ぶ |

種類に合わないフィールドは書けません。たとえば `kind: "summon"` に `ref` を付けるとスキーマ違反です。

### 7.2 Python関数への参照

`ref` は `module.path:callable` の形です。`research.tools:web_search` なら、生成コードは `research.tools` モジュールの `web_search` をインポートします。モジュールの各区切りと関数名には、英字・数字・アンダースコアを使い、先頭を数字にしません。

コロンの後は単一の名前です。`module:object.method`、関数呼び出し式、インラインPythonは指定できません。Pythonの予約語など、生成するimport文として使えない名前も避けてください。

道具の引数と戻り値の構造は `.jin` に定義しません。参照先のPython関数とADKのツール化の仕組みに委ねます。通常、モデルが道具を選び、引数を組み立てます。

`tools[].name` はJin内の識別名です。モデルから見える名前は、通常の道具ならPython関数名、`summon` なら参照先の陣名です。たとえばJin内で `search` と名付けても、上の関数はモデルから `web_search` と見えます。同じ陣に、実行時の名前が衝突する道具を並べないでください。

### 7.3 組み込み道具

`builtin` は、対象ADKの `google.adk.tools` が公開するツールの実体や関数を指定します。`FunctionTool` のようなクラス名を指定して、Jinにインスタンスを作らせるものではありません。使える名前はインストールされた対象バージョンに依存し、生成時に検査されます。

`exit_loop` はループの終了を要求する道具です。登録しただけでは呼ばれません。`google_search` などには、モデルやほかの道具との併用に制約があるため、組み込み名が正しいことだけでは実行成功を保証しません。

### 7.4 呼び出すか、引き継ぐか

| 指定 | 意図 | ADKへの変換 |
|---|---|---|
| `summon` | 別の担当へ作業を依頼し、結果を受け取る | `AgentTool(agent=...)` |
| `delegate` | 別の担当へ制御を引き継げるようにする | `LlmAgent.sub_agents` |
| `flow.steps` | 決めた進め方に従って担当を動かす | workflow agentの `sub_agents` |

`delegate` は陣のフィールドに `"delegate": ["Helper"]` のように書きます。`Helper` を `circles` に定義してください。配列に書いた全員を順番に呼ぶ設定ではありません。引き継ぎはモデルの判断に依存します。

呼び出し元の記憶を `summon` 先が直接参照できるとは限りません。呼び出しに渡す内容と、呼び出し先自身の指示を設計してください。

## 8. 処理の前後にチェックや応答待ちを置く

`boundary` は、チェック関数の配列 `guards` と、応答待ちに対応させる道具名の配列 `await` を持ちます。どちらも省略時は `[]` です。次は `boundary` の値の部分例です。

```json
{
  "guards": [
    { "on": "before_model", "ref": "research.guards:pii_filter" },
    { "on": "before_tool", "ref": "research.guards:audit_log" }
  ],
  "await": ["publish"]
}
```

### 8.1 チェックを差し込む

`guards` の各要素には `on` と `ref` が必要です。`ref` の形式は道具と同じです。`on` で関数を呼ぶタイミングを選びます。

| `on` | タイミング |
|---|---|
| `before_agent` | 陣全体の実行前 |
| `after_agent` | 陣全体の実行後 |
| `before_model` | モデル呼び出し前 |
| `after_model` | モデル応答後 |
| `before_tool` | 道具の呼び出し前 |
| `after_tool` | 道具の応答後 |

生成時には、対応するADKのコールバック引数へ渡されます。同じタイミングに複数指定した場合は、宣言順のリストになります。関数の引数・戻り値・後続処理を止める条件はADKのコールバック契約に従います。Jinが共通の「真なら許可、偽なら拒否」という規則を加えるわけではありません。

進行役の陣で使えるのは `before_agent` と `after_agent` だけです。`pii_filter` という名前の関数を指定しても、個人情報の除去処理が自動で実装されるわけではありません。必要な検査をPython側に用意してください。

### 8.2 外部の応答を待つ

`await` には、同じ陣の `tools[].name` を指定します。対象は `kind: "tool"` のPython関数に限ります。対象の道具は `FunctionTool` の代わりに `LongRunningFunctionTool` で包まれます。

これは人の承認や時間のかかる処理に対応するための接続点です。承認画面、承認待ち状態の管理、結果を返して再開する仕組みは別途必要です。`await` の宣言だけで、公開前に人の承認が必ず行われるとは限りません。

## 9. 名前と参照の規則

### 9.1 名前の一意性と実行可能な名前

陣名はファイル全体で一意です。道具名と記憶名は、それぞれ同じ陣の中で一意にします。別の陣に同じ記憶名を宣言することはできますが、共有キーへの書き込みになる点に注意してください。

文字列として保存できる名前と、Pythonコードとして生成できる陣名の範囲には違いがあります。実行する陣名はPythonの識別子であり、予約語ではなく、UnicodeのNFKC正規形である必要があります。実用上は `Researcher`、`DraftWriter` のような英数字とアンダースコアの名前が分かりやすくなります。

`user`、`root_agent`、`LlmAgent`、`str` など、ADKや生成コードが使う名前は陣名に使えません。同じプログラムで使う組み込みツール名や、終了判定役の `<ループ名>_exit_check` と衝突する名前も避けます。予約名の完全な一覧は [codegen.pyの `RESERVED_NAMES`](../packages/jin-adk/src/jin_adk/codegen.py) が定義しています。

### 9.2 参照グラフと親子関係

陣を頂点、参照を矢印と考えると、プログラムは有向グラフになります。`flow.steps` と `delegate` は親子関係を作り、`summon` は呼び出し関係だけを作ります。

| 構成 | 扱い |
|---|---|
| 2つの進行役が同じ陣を子に持つ | `JIN013`。陣は複数の親を持てない |
| 同じ陣を `steps` に2回書く | 親子の参照辺が重複し、`JIN013`になる。反復には `loop` を使う |
| 2つの陣が同じ陣を `summon` で呼ぶ | 多重親にはならない。ただしほかの制約も満たす必要がある |
| `A → B → A` の参照がある | `JIN012`。3種類すべての参照を含めて循環を禁止する |

`loop` は循環参照で実装するのではなく、進行役が子の列を反復します。したがって、反復は使えても自己再帰・相互再帰は使えません。

`root` は定義済みの陣を指す必要があります。また実行可能な構成では、ほかの陣から `root` を `steps`、`delegate`、`summon` で参照することはできません。入口から到達しない陣は定義しても自動で実行されず、検証・コード生成ではその定義も検査されます。

## 10. 検証してエラーを直す

### 10.1 検証は段階ごとに進む

```text
JSONとして読めるか
  → 必須フィールド・型・値の形が正しいか
  → 名前・参照・可視範囲が整合しているか
  → ADKコードとして生成できるか
  → 実行環境で関数やモデルが動くか
```

最初の3段階を確認するのが `jin check` です。前の段階でエラーがあれば、次の段階には進みません。意味検査の段階では、検出した問題をまとめて返します。

JSON Schemaへの適合だけでは、参照の循環や記憶の可視範囲までは確かめられません。また、`jin check` の成功は、モデルの認証や外部関数の動作まで保証するものではありません。

### 10.2 診断コード一覧

| コード | 種別 | 原因と直し方 |
|---|---|---|
| `JIN001` | エラー | JSONの構文、重複キー、深すぎる入れ子など。指摘位置の記述を直す |
| `JIN002` | エラー | 必須フィールド、型、未知のキー、文字列制約など。フィールド表に合わせる |
| `JIN010` | エラー | 陣・道具・記憶の名前が重複。名前を分ける |
| `JIN011` | エラー | `summon` / `delegate` の陣、または終了条件の記憶が見つからない。参照名・可視範囲を確認する |
| `JIN012` | エラー | 参照が循環。呼び出し関係を見直す |
| `JIN013` | エラー | 陣への親子辺が複数ある。担当を分けるか参照を整理する |
| `JIN020` | エラー | 道具または記憶が1つの陣で12個を超える。別の陣へ分ける |
| `JIN022` | エラー | `core` と `flow` が両方ある、または両方ない。一方を指定する |
| `JIN030` | エラー | ループに `max` も `exit` もない。終了方法を指定する |
| `JIN031` | エラー | `steps` の陣名が未定義。定義か参照を直す |
| `JIN040` | 警告 | `--resolve` 時にPython参照を解決できない。モジュールの配置や関数を確認する |
| `JIN050` | エラー | `{key}` が可視な記憶にない。宣言と処理順を確認する |
| `JIN060` | エラー | `root` が未定義の陣を指す。入口の名前を直す |
| `JIN070` | 警告 | `await` の道具名が同じ陣にない。`tools[].name` に合わせる |

`jin check` はエラーがあれば終了コード1を返します。警告だけの場合は0です。`JIN040` と `JIN070` を、実行可能であることの保証と取り違えないでください。

```bash
uv run jin check examples
uv run jin check --json hello.jin
```

JSON形式の診断には、`file`、`pointer`、`range`、`code`、`severity`、`message`、`hint` が入ります。`range` の行と列は1始まりで、列はUnicodeコードポイント単位です。終端位置は最後の文字の次を指します。言語サーバが使うLSPの座標は0始まり・UTF-16単位で、境界で変換されます。

### 10.3 生成時に見つかる問題

`jin build` と `jin run` は、意味検査の後にADKへの変換条件を調べます。代表的な失敗は、複数の `out: true`、実行できない陣名、道具の実行時名の衝突、形式の不正な `ref`、非対応の組み込み道具です。

進行役にモデル用のフィールドを付けた場合、`await` が `summon` / `builtin` を指す場合、JinとADKで解釈が異なる指示文もここで拒否します。これらは `BuildError` として原因・修正のヒント・対象位置を示し、終了コード1を返します。`JIN` 診断コードが増えるわけではありません。

## 11. コード生成と実行

### 11.1 Pythonコードを生成する

```bash
uv run jin build hello.jin --out /tmp/jin-manual-build
```

出力先には、入口の陣名を使ったパッケージ（この例では `Greeter/`）と環境設定のひな型が作られます。生成コードの `root_agent` が入口です。既存の生成物の上書きには `--force` が必要です。

| Jin | 生成する主なADK要素 |
|---|---|
| `core` を持つ陣 | `LlmAgent` |
| `sequence` / `parallel` / `loop` | `SequentialAgent` / `ParallelAgent` / `LoopAgent` |
| `flow.max` | `max_iterations` |
| `flow.exit` | ループ末尾の `StateCheckAgent` |
| `state.out: true` | `output_key` |
| 通常の道具 / `await` 対象の道具 | `FunctionTool` / `LongRunningFunctionTool` |
| `summon` | `AgentTool` |
| `delegate` | モデル付き陣の `sub_agents` |

生成コードはJinのパッケージを読み込まず、ADKと参照先のPythonコードを使います。終了判定役の処理も生成物に含むため、Jin側を更新したら必要に応じて再生成してください。

### 11.2 `jin run` で実行する

```bash
uv run jin run approval.jin "学内に自習室を増やす" --model fake --trace /tmp/jin-manual-trace.jsonl
```

`jin run` は一時ディレクトリへコードを生成して読み込み、記憶を初期化して実行します。疑似モデルでは `approved` に `fake-response` が入るため終了条件は一致せず、上の例は3周します。

`--model` で指定できるのは `fake` です。実モデルを変えるときは `.jin` の `core` を変更します。既定の疑似モデルは道具を呼び出さないので、道具の実装や承認待ちの検証には別の試験が必要です。

実行ごとに新しいメモリ上のセッションを作ります。`--session` に同じIDを渡しても、前回の記憶は引き継ぎません。生成物をADKのCLIで直接実行する場合は、`jin run` が行う記憶の `None` 初期化やJin用のトレース付与も行われません。

### 11.3 外部コードを読み込む範囲

通常の `jin check`、描画、エディタでの表示・編集は、`ref` のPythonコードをインポートしません。`jin build` はユーザーの `ref` を実行せずコード化しますが、組み込み道具の検査ではADKのモジュールを読み込みます。

`jin check --resolve` と `jin run` は、参照先の任意のPythonコードを実行します。内容を確認したコードを使ってください。`--model fake` はモデル呼び出しを置き換えるだけで、Pythonのインポートを無効にするものではありません。

`--resolve` は参照ごとの子プロセスで検査し、30秒でタイムアウトします。子プロセスも同じ権限で動きます。参照先はPythonの探索パスで解決し、作業ディレクトリを自動では加えません。必要なら `PYTHONPATH` を指定します。`jin run` は生成コードのインポート中だけ作業ディレクトリも探索対象に加えますが、実行中に遅れて読み込むモジュールは `PYTHONPATH` などで解決できる必要があります。

## 12. 魔法陣の読み方

### 12.1 要素と見た目の対応

図は装飾だけではなく、定義した構造を表しています。モデル付きの陣では、中心の核から外側へ、指示・道具・記憶・境界が配置されます。

| 要素 | 見た目 | `data-jin-kind` |
|---|---|---|
| 陣 | 全体のまとまり | `circle` |
| モデル | 中心の核 | `core` |
| 指示 | 指示環の文字列 | `rune` |
| 道具 | 道具環の紋と放射線 | `tool` |
| 記憶 | 記憶環の四角 | `state` |
| 進行 | 弦、矢印、節、終了条件の菱形 | `flow-edge` |
| チェック | 境界環の刻印 | `guard` |
| 応答待ち | 境界環の欠け | `await` |
| 引き継ぎ | 小円と破線 | `delegate` |

`sequence` は開いた矢印の列、`parallel` は弦のない対称配置、`loop` は閉じた多角形で表します。要素が5個以上のループは星形になることがありますが、矢印の訪問順は `steps` の順序に対応します。

### 12.2 配置と表示範囲

通常の紋は12時の位置から時計回りに、配列順で等間隔に並びます。正規化した半径は、指示が0.35、道具が0.55、記憶が0.75、境界が0.95です。存在しない環は描かず、残りの環を内側へ詰めません。モデルを持たない進行役では、これらの同心環は描きません。

呼び出し先などの入れ子の展開は深さ1までです。それより先は点で表し、詳しく見るには焦点を切り替えます。これは表示の省略であり、実行される陣を削る規則ではありません。

```bash
uv run jin render examples/researcher/researcher.jin --focus Summarizer -o /tmp/jin-summarizer.svg
```

同じモデルと同じ描画オプションからは、同じSVGが生成されます。座標は統一した丸め規則を使い、指示文由来の装飾はSHA-256で決まります。乱数や時刻を使って見た目を変えません。CLIの描画は意味検査にエラーがあるファイルを拒否します。

### 12.3 図とソースを結ぶ位置情報

各描画要素は `data-jin` にJSON Pointerを持ちます。JSON PointerはJSON内の値を指すパスで、`/circles/0/tools/2` は最初の陣の3番目の道具です。配列の添字は0始まり、文書全体は空文字列で表します。キー内の `~` は `~0`、`/` は `~1` とエスケープします。

同じ位置情報を、図の選択、診断、実行履歴で使います。配列を並べ替えると指す内容が変わるため、JSON Pointerは編集をまたいで不変のIDではありません。

## 13. 実行履歴を読む

`jin run --trace` は、実行履歴を1行1JSONのJSONL形式で保存します。各行には `seq`、`ts`、`agent`、`kind`、`name`、`pointer`、`input`、`output` が入ります。`seq` は1始まりの連番、`ts` はイベント時刻です。

| `kind` | 表すもの |
|---|---|
| `model` | 確定したモデル応答など |
| `tool` | 道具の呼び出し、または応答。引数は `input`、戻り値は `output` |
| `transfer` | 別の担当への制御の引き継ぎ |
| `escalate` | ループの終了判定や、途中での終了要求 |
| `final` | 実行全体の最後の行が `model` のとき、その行に付ける種別 |

`escalate` は「終了した」という意味だけではありません。状態判定は不一致の回も記録し、`output.matched` が成立の有無を示します。最後が判定イベントなら `final` 行はありません。

対応先を特定できないイベントは `pointer: null` のまま残り、理由が標準エラー出力に出ます。部分的なストリーミング応答は記録しません。また、現在の `summon` の内部実行イベントは外側のトレースに現れず、呼び出しと応答を中心に記録します。図の一部が光らないことだけで、実行されなかったとは判断できません。

```bash
uv run jin render approval.jin --trace /tmp/jin-manual-trace.jsonl --upto 2 -o /tmp/jin-approval-trace.svg
```

`--upto 2` は `seq <= 2` のイベントまでを重ねる指定です。エディタの「デバッグ」でも履歴を読み込み、タイムラインを動かせます。読み込み後にプログラムの配列を変更すると、古い位置情報が別の要素を指す可能性があるため、元のファイルと組み合わせて確認してください。

トレースにはモデルの出力や道具の引数などが入ります。ファイルは所有者だけが読み書きできる権限で保存されますが、共有前には内容を確認してください。

## 14. 整形とエディタでの編集

### 14.1 正準形にそろえる

正準形は、同じモデルをいつも同じ書式で保存するための規則です。`jin fmt` とエディタの保存は、同じ正準形を使います。

```bash
uv run jin fmt hello.jin
uv run jin fmt --check hello.jin
```

インデントは2スペース、キーはモデルの定義順、配列は宣言順を保ちます。`$schema` と `version` を先頭に置き、末尾には改行を1つ付けます。日本語はUTF-8のまま保存し、既定値と同じ省略可能なフィールドは省きます。たとえば `out: false` や `tools: []` は出力しません。

一度整形した結果を再び整形しても変わりません。これは冪等性と呼ばれる性質です。整形によってプログラムのモデルは変わりませんが、空白やキーの元の並びは保持されません。

### 14.2 名前変更と取り消し

エディタは図の選択をJSON Pointerへ対応させ、モデルに対する編集操作をサーバへ送ります。主な操作は陣・道具・記憶の追加や削除、指示や進行の変更、名前変更です。操作が返す逆操作を使って、取り消し・やり直しを行います。

`rename` で陣名を変えると `root`、`steps`、`delegate`、`summon` の参照も更新します。道具名では同じ陣の `await`、記憶名では一致する `{key}` と `exit.key` が更新対象です。

記憶名の参照更新は、可視範囲だけに限定せず全陣を対象にします。同じ名前を複数の陣で使っている場合は、変更後の参照を確認してください。記憶宣言の名前だけを直接書き換える操作と、参照を追随させる `rename` は同じではありません。

構文が壊れている間、エディタは直前の正常なモデルを表示することがあります。その場合は古い表示であることを示します。意味編集の操作を古いモデルに適用して書き戻すことはしません。

## 15. 対応範囲と参照資料

v1で扱う中心的な機能は、モデルへの指示、Python・組み込み・別の陣の道具化、引き継ぎ、記憶、順次・並列・反復、チェック、応答待ちの宣言です。

Jin構文として、一般の計算式、任意の条件分岐、再帰、複数ファイルの `import`、記憶の永続化は用意していません。ADKの `planner`、`output_schema`、MCP接続の設定、`code_executor` などを直接記述するフィールドもありません。エディタのデバッグは記録済みの履歴の再生であり、ライブ実行を制御するデバッガではありません。
